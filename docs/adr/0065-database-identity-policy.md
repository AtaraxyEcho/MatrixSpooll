# 数据库身份与主键策略

MatrixSpooll 的数据库同时承载用户可见实体、运行时队列和审计事实。它们的身份语义不同，不能用一次“全部改成 UUID”的机械迁移替代领域设计。

## 决定

- 用户、项目、任务、资源、登录会话和 Agent 会话等会被 API、文件路径或权限系统引用的实体，主键使用应用生成的 UUID 字符串。`default` 不再承担任何身份语义；环境配置的超级管理员由 `is_superadmin` 标记识别。
- 项目展示名称不是身份。项目表的 UUID 与不可变 `storage_key` 分别承担数据库关系和本地目录定位；名称只用于列表展示和用户输入解析。
- 需要保持请求协议兼容的模型标识继续由 provider/model 层维护。例如自定义供应商的 `custom-N` 是既有外部协议标识，不直接暴露数据库自增键的替换值。将它改成 UUID 必须另行迁移数据库、配置、项目 JSON、队列和前端协议，不能在身份加固迁移中静默完成。
- 追加型调用、用量、审计事实表可使用自增整数作为内部排序键；它们通过 `actor_user_id`、`project_id`、时间和资源字段建立归属，不作为用户可寻址资源。
- 关联表和租约表可以使用复合业务键（例如项目成员、worker lease），但必须保留对应的唯一约束和外键。会话转录表的序列键用于 SDK 顺序语义，不能删除或改写为 API 资源 ID。
- 所有新表必须在建模评审中明确：对外实体 UUID、内部事实自增键、还是复合关联键；迁移必须先回填并验证唯一性，再切换约束。

## 后果

核心权限和项目隔离查询只依赖 UUID `project_id`/`user_id`，重复项目名称不会串租户。内部事实表保留紧凑键，避免无意义的全链路协议变更与历史数据重写。

任何需要让现有内部键对外可见的功能，必须新增稳定 UUID 资源标识，而不是把数据库自增值直接提升为公共 API 契约。
